<Aside type="note" title="Protocol v1.3 — Quantum AI Lab">
Everything on this page is additive over v1.2: new message types only. Clients
that never send a `trainability_*` or `discovery_*` message see no change.
Every example is a fixture replayed against the real kernel handlers by
`kernel/tests/test_docs_fixtures.py` (single replies) and
`kernel/tests/test_docs_lab_fixtures.py` (streams). Fields that vary run to run
(timings, fingerprints, library versions) show as `"<any>"`, and floating-point
values as `"<approx:value:tolerance>"`.
</Aside>

## Conventions

- **Authenticate first** (protocol v2). Every Lab connection begins with
  `{"type": "authenticate", "token": "<token>"}` and waits for
  `{"type": "authenticated"}`; see [Authentication](/docs/kernel-api/overview/#authentication).
  The examples below show the messages that follow the handshake, and the
  replay tests send the handshake through the real authentication gate before
  every fixture.
- Replies are flat `{"type": ...}` objects. Failures are
  `{"type": "error", "phase": "trainability" | "discovery", "code", "message"}`
  plus `job_id`, `run_id`, `candidate_id`, `path` or `column` where they apply.
- **Sync requests** (`trainability_inspect`, `trainability_lint`, the `*_cancel`
  messages, `discovery_evaluators`, `discovery_mutate`, `discovery_conjecture_schema`)
  answer with one message.
- **Job requests** (`trainability_start`, `discovery_evaluate`, `discovery_audit`,
  `discovery_conjecture_test`) run in subprocesses and stream. The client
  chooses the id for trainability and conjecture jobs (`job_id`); discovery
  jobs are keyed by `run_id` and `candidate_id`. A job always ends with its
  terminal message, even when cancelled.
- Closing the WebSocket cancels every job the connection owns.
- A web build has no kernel; the Lab needs the desktop app (or a kernel you run yourself).

### `trainability_inspect`

Executes the code once (same trust as `execute`), finds the parameterized
circuit and reports what the Lab can analyze. Optional fields: `language`,
`params`.

The editor-time lint: rules TRN001 to TRN007 under a 0.35 s compute budget.
`observable` is optional (the code's `nuclei_observable`, else `preset:local_z`).

`summary.skipped_rules`, if it does not finish in time.

### `trainability_start`

Starts an analysis job. Required: `job_id` (client-chosen, at most 128 characters),
`code`, `observable` (may be empty). Optional: `language`, `params`, `analyses`
(a subset of `gradients`, `scaling`, `lie`, `expressibility`, `entanglement`,
`landscape`) and `settings` (clamped; the clamped values come back in
`provenance.settings`).

Stream: `trainability_started`, `trainability_progress` (at most about 10 per second,
omitted from the fixture), one `trainability_partial` per finished analysis, then
`trainability_result` with `status` `complete`, `cancelled` or `failed`, per-analysis
`results` and `errors`, and the `provenance` block that powers the
[Trainability Certificate](/docs/research/trainability-lab/#the-trainability-certificate).

<Code code={tsStream} lang="json" title="lab/trainability_start.stream.json" />

At most 2 jobs run per connection and 4 globally; more answer `trainability_busy`.
Jobs are killed after 20 minutes. A request with no `job_id` is refused:

### Trainability error codes

| Code | Meaning |
|------|---------|
| `invalid_request` | A field is missing or the wrong type |
| `invalid_observable` | The observable does not parse; carries `column` |
| `compile_error` | The code has a syntax error |
| `unbound_parameters` | The circuit still has free symbols the code never binds |
| `ppe_not_applicable`, `ppe_required` | The exact Pauli-propagation engine was requested (or needed beyond 20 qubits) but the circuit is outside its class |
| `analysis_unavailable`, `analysis_failed` | The analysis could not run, or raised |
| `out_of_memory` | The analysis exhausted memory |
| `trainability_busy` | Too many jobs for this connection or kernel |

Error codes raised by the circuit converters (for example an unsupported gate) are passed through with their own code.

### `discovery_evaluators`

Lists the registered evaluators. Each entry carries `kind`, `version`, `title`,
`description`, `task`, `entry_signature`, `objectives`, `descriptors`, a JSON

<Code code={deReq} lang="json" title="lab_discovery_evaluators.request.json" />
<Code code={deRes} lang="json" title="lab_discovery_evaluators.responses.json" />

Kinds: `qec_memory`, `state_synthesis`, `vqe_ground_state`, `trainability_frontier`.

### `discovery_evaluate`

Scores one candidate program. Required: `run_id`, `candidate_id`, `evaluator`
(`{kind, config}`), `program`, `seed`. Optional: `entry` (default per
evaluator), `stage` (`screen`, `full`, `confirm`; default `full`).
The reply is `discovery_evaluate_accepted` with a `queue_position`, then later
one `discovery_evaluation` carrying the evaluation record.

<Code code={evStream} lang="json" title="lab/discovery_evaluate.stream.json" />

The record is always returned, whatever happened: `status` is `scored`,
`rejected` (a guardrail failed; see `rejection` and the `guardrails` list,
in which later guardrails are `skipped`) or `failed` (the sandbox or scorer
broke; see `failure`). `isolation` says how the candidate was contained:
`sandbox-exec` (macOS), `bwrap` (Linux) or `process`.
`cache_hit: true` means an in-kernel LRU (512 entries, keyed by program,
fingerprint, seed and stage) answered.

Errors: an unknown kind and a config that fails the schema.

## Red Queen audits (`discovery_audit*`)

An audit re-scores a candidate's artifact independently of the evaluator and
compares the two (see [Red Queen mode](/docs/research/discovery-engine/#red-queen-mode)).

### `discovery_audit`

Required: `run_id`, `candidate_id`, `evaluator`, `program`, `seed` and
`evaluation` (the record the evaluator produced, with a valid `status`).
Evaluators without an audit answer `audit_unavailable`.
The reply is `discovery_audit_accepted`, then `discovery_audit_result`.
`audit.verdict` is `consistent`, `exploit` or `inconclusive`; `gap` is
evaluator fitness minus audit fitness; every `checks[]` entry is shown, passed or not.

## Conjecture Engine (`discovery_conjecture*`)

### `discovery_conjecture_schema`

Returns what a conjecture may say: the structural `features` a predicate can
filter on, the `quantities` a prediction can bound, the test-family JSON Schema
(`families`), the predicate grammar and the `limits` (circuits 5 to 32, points
4 to 8, n up to 128, 60 s per circuit, 600 s total). The app validates every
model-proposed conjecture against this reply, so the model cannot propose what
the kernel will not run.

<Code code={cjsReq} lang="json" title="lab_discovery_conjecture_schema.request.json" />
<Code code={cjsRes} lang="json" title="lab_discovery_conjecture_schema.responses.json" />

### `discovery_conjecture_test`

Required: `job_id`, `conjecture`, optional `seed` (0 to 2^31 - 1, default 0).
Stream: `discovery_conjecture_started`, `discovery_conjecture_progress`
(throttled; omitted from the fixture), one `discovery_conjecture_evidence` per
held-out circuit, then `discovery_conjecture_result` with `status`
`complete`, `cancelled` or `failed`. A `complete` result carries a
`verdict` (`supported`, `refuted` or `inconclusive`), a `tally`, the evidence,
any `counterexamples` (each with the IR needed to rebuild the circuit) and a
`fingerprint` of the tester.

The example below is a real run, and it is a refutation: the conjecture
claimed that brick-pattern CZ circuits with Y and Z rotations keep
`beta_upper95` below 0.1 under a local observable; every one of the five
held-out circuits violated it. Evidence and counterexample bodies are
summarized as `"<any>"` in the fixture.
