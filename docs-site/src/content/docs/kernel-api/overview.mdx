The Nuclei kernel is a standalone WebSocket service. The desktop frontend is
just its first client — anything that can open a WebSocket and speak JSON can
parse circuits, run simulations, and submit hardware jobs. This section
documents that protocol as a public API.

<Aside type="note" title="Protocol v1">
The kernel protocol is public and stable-intent. Until Nuclei 1.0 it may
still evolve: **additive** changes (new message types, new optional fields)
can land without notice, and clients must ignore unknown fields and unknown
response types. **Breaking** changes ship only with a protocol version bump
and an entry in the
[protocol changelog](/docs/reference/protocol-changelog/).
</Aside>

## Connection

{/* Constants: server.py:14-18; bind loop: server.py:495-513 */}

| Property | Value |
|----------|-------|
| URL | `ws://localhost:9742` |
| Port fallback | If 9742 is taken, the kernel scans upward through `9742`–`9761` (range of 20) and binds the first free port |
| Framing | JSON text frames — one request or response object per frame |
| Max inbound message | 1 MiB (`1_048_576` bytes); larger frames close the connection |
| Heartbeat | WebSocket ping every 30 s; connection dropped after a 20 s pong timeout |
| Auth | Per-launch token, presented in the first frame (see [Authentication](#authentication)) |

Requests on one connection are processed strictly in order: the handler
fully finishes (and sends every response for) request *N* before reading
request *N + 1*. For concurrent work, open multiple connections — each
connection gets its own isolated `Executor` (parse/execute state never
bleeds between clients), while hardware state (provider connections, job
registry) is shared process-wide. {/* server.py:20-23, 162-167 */}

## Authentication

The kernel executes code it receives, so every connection must authenticate
before any request is handled. This is **protocol v2** and it is breaking for
external clients: a client that does not send the `authenticate` frame first
is disconnected. See the [protocol changelog](/docs/reference/protocol-changelog/).

1. The kernel reads a secret token from `NUCLEI_KERNEL_TOKEN` (the desktop app
   generates a fresh one per launch). With no token it refuses to start.
2. It writes the token and port to a user-only (`0600`) runtime file,
   `~/.nuclei/runtime/kernel.json` (override the directory with
   `NUCLEI_RUNTIME_DIR`), so local scripts can read it. Scripts can use
   `$NUCLEI_KERNEL_TOKEN` instead when they launched the kernel themselves.
3. The first frame on a connection must be
   `{"type": "authenticate", "token": "<token>"}`. The kernel answers
   `{"type": "authenticated"}` and only then handles requests. The token is
   never sent in the URL.
4. Browser connections must also come from an allowed `Origin`, and the `Host`
   header must be a loopback name on the kernel's port. Scripts that send no
   `Origin` are accepted only with the token.

Every socket the app opens authenticates this way: the editor's, the Trainability
Lab's, the Discovery Engine's, and the audit and conjecture sessions. Replies
in the [Quantum AI Lab messages](/docs/kernel-api/messages-lab/) examples start
after the handshake.

### How a connection is refused

| Situation | Result |
|-----------|--------|
| Foreign `Origin` or non-loopback `Host` | HTTP `403` on the WebSocket upgrade; the connection never opens |
| First frame is not a valid `authenticate` frame, wrong token, or no frame within 10 s | Closed with code `4401` |
| Request sent before the `authenticated` ack | Not handled; the connection is closed with `4401` |

A client library's "connection refused with 403" therefore means the `Origin`
or `Host` is wrong, and a `4401` close means the token is wrong or missing.

For throwaway local experiments only, `NUCLEI_KERNEL_INSECURE_DEV=1` disables
authentication and prints a warning. The kernel never passes its token to the
processes it starts (code execution, Lab workers, the discovery sandbox).

## Running the kernel standalone

```bash
cd kernel && NUCLEI_KERNEL_TOKEN="$(python -c 'import secrets; print(secrets.token_urlsafe(32))')" python server.py
```

On success the kernel prints exactly one ready line to stdout:

```text
Nuclei kernel ready on ws://localhost:9742
```

This line is the port-discovery contract: when the default port was taken,
the chosen port appears in this line, on its own line, flushed — parse it
rather than assuming 9742. {/* server.py:506 */}

## The streaming model

A request does not get *a* reply. It produces an ordered **sequence** of
response messages on the same connection, ending with a request-specific
final message (`result` for `execute`, `python_result` for `run_python`,
`snapshot` for `parse` — though a failed parse appends one `error` after
it — and a single reply for every `hardware_*` request). Streamed `output` / `stderr` messages may interleave before the
terminal message, so a robust client loops until it sees the terminal type
— see [client examples](/docs/kernel-api/client-examples/).
